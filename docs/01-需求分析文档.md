## 1. 背景与目标

### 1.1 现状痛点

- 售后咨询占客服进线量约 60%，其中"我的快递到哪了""能不能退"两类高度同质，人力消耗大但价值密度低。
- 退款申请横跨订单、物流、支付、风控四个系统，坐席平均处理时长 4~6 分钟，高峰期积压。
- 现有机器人是"关键词 + 话术树"，一旦用户换个说法就掉进兜底，转人工率高。

### 1.2 目标

| 指标 | 现状 | 目标（上线 3 个月） |
|---|---|---|
| 售后类咨询自动解决率 | 22% | ≥ 55% |
| 退款申请平均处理时长 | 4.5 min | ≤ 40 s（自动）/ ≤ 2 h（需审批） |
| 误退款率（不该退却退了） | 0.8% | ≤ 0.1% |
| 用户满意度 CSAT | 78 | ≥ 85 |
| 转人工率 | 62% | ≤ 35% |

### 1.3 非目标（本期明确不做）

- 不做换货 / 维修 / 价保的完整链路（仅做规则判断后转人工）。
- 不做多语言，不做语音渠道。
- 不做真实支付通道退款，仅生成退款指令并由既有清结算系统消费。

## 2. 术语与角色

### 2.1 术语

| 术语 | 定义 |
|---|---|
| 会话（Session） | 一次用户与 Agent 的连续交互，有独立状态机与过期时间（默认 30 分钟无活动过期） |
| 退款单（Refund） | 一次退款诉求的业务实体，独立于会话存在，会话结束后仍可查询 |
| 工具（Tool） | Agent 可调用的原子业务能力，有严格 JSON Schema 入参出参 |
| 决策码（Decision Code） | 规则引擎输出的结构化结论，如 `OK_AUTO`、`REJECT_EXPIRED` |
| 确认令牌（confirm_token） | 用户确认方案后签发的短期凭证，是执行退款的唯一凭证 |
| 审批等级 | L1 客服主管 / L2 财务，按退款金额分档 |
| 幂等键（idempotency_key） | 同一意图重复提交时保证只产生一笔退款 |

### 2.2 角色

| 角色 | 关注点 | 系统能力 |
|---|---|---|
| 消费者（终端用户） | 快、准、别让我重复描述 | 自然语言提问、查看方案、确认/取消 |
| AI Agent | 理解诉求、调工具、解释规则 | 会话编排、工具调用、方案生成 |
| 客服坐席 | 接管复杂单、给特批 | 会话接管、查看 Agent 全过程、override |
| 客服主管（L1） | 500~2000 元退款审批 | 审批工作台、批量审批 |
| 财务（L2） | >2000 元退款审批、对账 | 双签审批、导出对账 |
| 运营 | 规则可调、效果可看 | 规则配置、指标看板、badcase 回流 |
| 风控 | 防薅羊毛 | 风险标签、强制人工名单 |

## 3. 业务流程

### 3.1 主流程（Happy Path）

```
用户提问
  → 意图识别（订单/物流/退款/其他）
  → 提取订单号（缺失则引导提供，最多追问 2 次）
  → 身份校验（订单号 + 手机尾号4位，或已登录态直接绑定）
  → 装载上下文（订单快照、物流快照、会员等级、风控标签、适用规则版本）
  → [查询类] 直接组织答案返回
  → [退款类] 规则引擎判定
        ├ 不可退 → 解释原因 + 给替代方案（换货/维修/转人工）
        └ 可退   → 生成方案卡（金额拆解、退回方式、时效）
              → 等待用户确认（confirm_token 10 分钟）
              → 用户确认
              → 金额 ≤ 阈值 → 自动通过 → 提交清结算
              → 金额 > 阈值 → 建审批任务 → 通知审批人 → 审批通过后提交
  → 回写状态 + 消息通知 + 审计留痕
```

### 3.2 关键分支与异常

| 分支 | 触发条件 | 系统行为 |
|---|---|---|
| B1 订单号缺失 | 用户未提供且会话无上下文 | 追问，2 次仍未给则引导"我的订单"列表选择 |
| B2 身份不符 | 手机尾号不匹配 | 拒绝披露订单详情，提示验证方式，3 次失败锁 10 分钟 |
| B3 订单不存在 | 查无此单 | 提示核对，提供"最近订单"兜底 |
| B4 不可退 | 规则判定拒绝 | 说明具体规则 + 替代方案，可一键转人工 |
| B5 需补凭证 | 超 7 天但主张质量问题 | 引导上传图片/视频，凭证到位后转人工判定 |
| B6 用户改主意 | 方案已展示未确认 | 允许改数量/改原因，重新判定（旧草稿作废） |
| B7 确认超时 | token 过期 | 提示"方案已失效，是否重新生成" |
| B8 重复提交 | 同订单已有进行中退款 | 幂等拦截，返回已有退款单进度 |
| B9 审批超时 | 审批任务超 SLA（4h） | 升级至上级 + 通知，Agent 告知用户预计延迟 |
| B10 执行失败 | 清结算返回失败 | 退款单置 FAILED，重试 3 次，仍失败转人工 |
| B11 用户情绪激烈 | 命中投诉/辱骂/消协关键词 | 跳过流程直接转人工，标记高优先级 |
| B12 用户要求人工 | 明确说"转人工" | 立即转，附会话摘要，不让用户重复描述 |

## 4. 功能需求

优先级：P0 = MVP 必须；P1 = 首个迭代内；P2 = 后续增强。

### FR-01 意图识别与槽位抽取（P0）

- 识别五类意图：`ORDER_QUERY`、`LOGISTICS_QUERY`、`REFUND_REQUEST`、`POLICY_FAQ`、`OTHER`。
- 槽位：`order_no`、`phone_tail4`、`reason_code`、`refund_type`、`item_ids`、`qty`、`evidence`。
- 支持多轮补槽，单轮最多追问 1 个槽位（避免一次问 4 个问题）。
- 一句话含多意图时按优先级处理：退款 > 物流 > 订单 > FAQ。
- **验收**：500 条标注集上意图准确率 ≥ 92%，槽位 F1 ≥ 0.9。

### FR-02 订单查询（P0）

- 按订单号查询订单状态、商品、金额、时间节点。
- 未提供订单号时，按用户维度返回最近 3 笔订单供选择。
- 输出必须做脱敏：手机号 `138****8888`、地址只到区。
- **验收**：查询成功率 100%（库内有单），P95 响应 < 800 ms。

### FR-03 物流查询（P0）

- 返回承运商、运单号、当前状态、最近 3 条轨迹、预计送达。
- 异常件（滞留/丢件/退回）主动提示并给出下一步（催件/补发/退款）。
- 物流接口超时时，降级返回订单页缓存的最后状态，并注明"数据可能延迟"。
- **验收**：轨迹展示与物流商后台一致率 100%；超时降级不报错。

### FR-04 退款资格判定（P0，核心）

规则引擎输入：订单快照、明细、物流状态、规则版本、用户风控标签、历史退款次数、申请原因、当前时间。
输出结构化决策：

```json
{
  "eligible": true,
  "decision_code": "OK_NEED_APPROVAL_L1",
  "refund_type": "RETURN_REFUND",
  "amount": { "goods": 1880.00, "freight_refund": 0, "freight_deduct": 0, "total": 1880.00 },
  "need_manual_approval": true,
  "approval_level": 1,
  "requires_evidence": false,
  "reasons": ["已发货未签收，需物流拦截或拒收"],
  "policy_version": 3
}
```

- 规则见第 6 节，全部可配置（`refund_policies.rule_json`），代码内有兜底默认值。
- **验收**：规则用例集 60 条全部通过；同输入同规则版本输出必须完全一致（纯函数）。

### FR-05 方案展示与确认（P0，核心）

- 方案卡必须包含：退款类型、退款金额拆解（商品/运费/优惠扣回）、退回方式、预计到账时效、需用户配合事项。
- 方案生成后进入 `PROPOSAL_PENDING`，**不落正式单、不触发任何资金动作**。
- 用户确认才调用 `confirm_refund`；否定/修改则回到判定或取消。
- 确认令牌 10 分钟有效，一次性消费。
- **验收**：确认前数据库不存在 `status != DRAFT` 的退款单；重复确认只产生一笔。

### FR-06 人工审批（P0，核心）

- 金额分档：≤500 自动；500 < x ≤ 2000 → L1 主管；> 2000 → L2 财务（可要求 L1 先审）。
- 强制人工条件（任一命中即走审批，不看金额）：风控等级 HIGH、同订单第 2 次退款、退款率异常、含特批商品。
- 审批动作：通过 / 驳回（必填理由）/ 转他人 / 要求补充材料。
- 审批结果回调 Agent，会话被唤醒并把结论转成用户话术。
- SLA：L1 4 小时，L2 8 小时，超时自动升级并通知。
- **验收**：审批结论 100% 落到退款单与消息；越权审批被拒绝。

### FR-07 执行退款（P0）

- 审批通过（或自动通过）后向清结算提交退款指令，写 `outbox_events` 保证最终一致。
- 幂等：`order_id + refund_seq` 唯一约束，重复指令返回既有结果。
- 失败重试 3 次（指数退避），仍失败转人工并标记 `FAILED`。
- **验收**：并发 100 次同单提交仅产生 1 笔退款。

### FR-08 转人工与接管（P0）

- 触发：用户主动要求、连续 3 轮未解决、命中风控/投诉词、工具连续失败。
- 转人工时必须带**会话摘要**（用户诉求、已查信息、已做判断、建议动作），坐席无需重问。
- 坐席接管后 Agent 静默，消息仍落库，交接可回看。
- **验收**：接管后 Agent 不再自动回复；摘要包含订单号与决策码。

### FR-09 会话记忆与状态恢复（P1）

- 短期记忆：会话内最近 10 轮 + 结构化槽位（存 `agent_sessions.state_payload`）。
- 长期记忆：用户历史退款次数、偏好、常用地址（只读，供规则使用）。
- 服务重启 / 跨实例：会话状态全在 DB，任意实例可续跑。
- **验收**：实例重启后继续对话，槽位不丢。

### FR-10 规则配置与灰度（P1）

- 运营可改：无理由天数、自动审批阈值、禁退类目、次数上限。
- 规则有版本号与生效时间，退款单记录判定时的 `policy_version`（事后可解释）。
- 支持按渠道/会员等级灰度不同规则版本。
- **验收**：改规则不影响已生成的退款单判定结果。

### FR-11 审计与可观测（P1）

- 全链路 `trace_id` 贯穿：用户消息 → LLM 调用 → 工具调用 → 规则判定 → 审批 → 执行。
- 记录每次工具调用的入参出参、耗时、错误码。
- 敏感字段（手机号、地址、身份证）日志脱敏。
- **验收**：任意一笔退款可在 30 秒内拉出完整链路。

### FR-12 话术与合规护栏（P0）

- 禁止承诺规则外内容（"肯定能退""马上到账"）。
- 禁止泄露其他用户信息、内部规则阈值原文（可说"根据平台售后规则"）。
- 输出前过一遍"承诺检测"（正则 + 小模型），命中则改写。
- **验收**：红线用例集 50 条零违规。

## 5. 非功能需求

| 类别 | 要求 |
|---|---|
| 性能 | 首字返回 P95 < 1.5 s；完整回答 P95 < 6 s；纯查询工具 P95 < 300 ms |
| 并发 | 峰值 500 QPS 会话，工具层 2000 QPS |
| 可用性 | 99.9%；LLM 不可用时降级为"菜单式引导 + 转人工"，不返回 5xx |
| 一致性 | 退款金额、状态变更强一致（事务）；通知类最终一致（outbox） |
| 安全 | 订单信息需身份校验；接口鉴权 JWT + 内部 mTLS；防重放 nonce |
| 合规 | 个人信息最小化存储；日志脱敏；退款操作留痕 ≥ 3 年 |
| 可维护 | 规则与话术外置配置，改规则不发版 |
| 成本 | 单次会话 LLM 成本 ≤ ¥0.06，缓存命中率 ≥ 30% |

## 6. 业务规则清单（可直接编码）

| 编号 | 规则 | 判定 | 命中结果 |
|---|---|---|---|
| BR-01 | 订单状态必须为 PAID / SHIPPED / DELIVERED / COMPLETED | 否 | `REJECT_STATUS` |
| BR-02 | 已取消 / 已关闭订单不可退 | 是 | `REJECT_STATUS` |
| BR-03 | 已支付未发货 → 取消退款，全额含运费 | 是 | `OK_AUTO`（CANCEL） |
| BR-04 | 已发货未签收 → 退货退款，需拦截/拒收 | 是 | `OK_*`（RETURN_REFUND） |
| BR-05 | 已签收 ≤ N 天（默认 7）→ 支持无理由 | 是 | 继续判金额 |
| BR-06 | 已签收 > N 天且原因为非质量 → 拒 | 是 | `REJECT_EXPIRED` |
| BR-07 | 已签收 > N 天但主张质量问题 → 需凭证 | 是 | `NEED_EVIDENCE` |
| BR-08 | 禁退类目（虚拟/定制/生鲜/已拆封个护/贴身衣物） | 是 | `REJECT_CATEGORY` |
| BR-09 | 同订单退款次数 ≥ 2 | 是 | 强制 L1 审批 |
| BR-10 | 同订单存在 REFUNDING/REFUNDED 记录 | 是 | `REJECT_DUPLICATE`（返回既有单） |
| BR-11 | 用户 30 天退款率 > 60% 或风控 HIGH | 是 | 强制 L2 + 人工复核 |
| BR-12 | 金额分档：≤500 自动 / ≤2000 L1 / >2000 L2 | 按金额 | 决定 approval_level |
| BR-13 | 无理由且原单包邮 → 扣回运费；质量问题 → 平台承担运费 | 按原因 | 影响 `freight_deduct` |
| BR-14 | 部分退款按明细行实付金额占比，含优惠分摊 | 按明细 | 计算行级金额 |
| BR-15 | 退款总额不得超过订单实付金额 | 是 | 截断 + 告警 |

**规则执行顺序**：BR-01/02 → BR-10 → BR-08 → BR-05/06/07 → BR-14/15 → BR-13 → BR-09/11/12。
短路原则：命中拒绝类规则立即返回，不再计算金额（避免给用户"差一点就能退"的错觉）。

**决策码枚举**：

| 码 | 含义 | 后续动作 |
|---|---|---|
| `OK_AUTO` | 可退且免审批 | 确认后直接执行 |
| `OK_NEED_APPROVAL_L1` | 可退，需主管审批 | 确认后建审批任务 |
| `OK_NEED_APPROVAL_L2` | 可退，需财务审批 | 确认后建审批任务（可含 L1） |
| `NEED_EVIDENCE` | 需补充凭证 | 引导上传，到位后转人工 |
| `REJECT_STATUS` | 状态不支持 | 解释 + 替代方案 |
| `REJECT_EXPIRED` | 超出售后期 | 解释 + 转人工通道 |
| `REJECT_CATEGORY` | 类目不支持 | 解释 + 转人工通道 |
| `REJECT_DUPLICATE` | 重复申请 | 展示既有单进度 |
| `NEED_HUMAN_RISK` | 风控命中 | 直接转人工 |

## 7. 状态定义

### 7.1 会话状态

`INIT` → `AUTH_VERIFY` → `INTENT_RESOLVED` → `COLLECTING_SLOT` ⇄ `TOOL_RUNNING` → `PROPOSAL_PENDING` → `EXECUTING` → `PENDING_APPROVAL` → `COMPLETED`；旁路终态 `ESCALATED`、`ABORTED`、`EXPIRED`。
详见 `04-功能编排与状态机.md`。

### 7.2 退款单状态

`DRAFT` → `ELIGIBLE` → `USER_CONFIRMED` → `PENDING_APPROVAL` → `APPROVED` → `PROCESSING` → `SUCCESS`；终态 `REJECTED_BY_RULE`、`REJECTED_BY_HUMAN`、`CANCELLED`、`EXPIRED`、`FAILED`。

---

## 8. 验收标准（Definition of Done）

1. 6 个演示场景（查询/物流/自动退/审批退/超期拒/类目拒）全部通过脚本断言。
2. 确认前无正式退款单；重复确认仅 1 笔；token 过期被拒。
3. 审批通过/驳回后用户端在 1 轮内收到结论。
4. 任意一笔退款可凭 `refund_no` 拉出完整事件链。
5. 红线话术用例零违规；手机号在日志中不可见。
6. 压测 500 QPS 下 P95 < 6 s，错误率 < 0.5%。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 模型幻觉编造订单信息 | 高 | 所有事实必须来自工具返回，系统提示强制"无工具结果不得陈述订单事实" |
| 模型擅自承诺退款 | 高 | 话术护栏 + 退款只能由 `confirm_refund` 落单 |
| 用户诱导越权（"你们主管同意了"） | 中 | 审批结论只认审批表，不认对话内容 |
| 规则配置错误导致误退 | 高 | 规则灰度 + 影子模式 + 金额异常告警（单日退款额环比 > 200% 熔断） |
| 物流接口不稳定 | 中 | 缓存降级 + 超时 800ms 快速失败 |
| LLM 成本超预算 | 中 | 小模型做意图分类、大模型只做方案解释；结果缓存 |
