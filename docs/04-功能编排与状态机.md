# 功能编排与状态机 · AI 客服与售后 Agent

> 本文回答一个问题：**一条用户消息进来，系统按什么顺序做什么事，出问题时怎么退。**

---

## 1. 编排总览

```
                         ┌──────────────┐
                         │ 消息入口      │ 幂等去重 / 会话锁 / 限流
                         └──────┬───────┘
                                ▼
                    ┌───────────────────────┐
                    │ N0 预处理              │ 敏感词 / 注入检测 / 转人工意图
                    └──────┬────────────────┘
                           ▼
                    ┌───────────────────────┐
                    │ N1 意图 + 槽位         │ 小模型分类 → 大模型补槽
                    └──────┬────────────────┘
              ┌────────────┴────────────┐
              ▼                         ▼
      ┌──────────────┐          ┌──────────────┐
      │ N2 查询类     │          │ N3 退款类     │
      │ 订单/物流/FAQ │          │ 校验→判定     │
      └──────┬───────┘          └──────┬───────┘
             │                         ▼
             │                  ┌──────────────┐
             │                  │ N4 方案构建   │ 金额拆解 + 话术
             │                  └──────┬───────┘
             │                         ▼
             │                  ┌──────────────┐
             │                  │ N5 确认闸门   │ ◀── 等待用户
             │                  └──────┬───────┘
             │                         ▼
             │                  ┌──────────────┐
             │                  │ N6 执行分流   │ 自动 / 审批
             │                  └──────┬───────┘
             └────────────┬────────────┘
                          ▼
                   ┌──────────────┐
                   │ N7 回写+通知  │ 状态、消息、审计、指标
                   └──────────────┘
```

设计要点：**N4-N6 是不可跳过的三段式**。任何"直接退款"的路径都必须经过"方案 → 确认 → 执行"，这是审计与合规的底线。

## 2. 节点定义

| 节点 | 职责 | 输入 | 输出 | 失败处理 |
|---|---|---|---|---|
| N0 预处理 | 敏感词、Prompt 注入、投诉倾向、空消息 | 原始文本 | `{blocked, escalate, cleaned}` | 命中投诉词直接 `ESCALATED` |
| N1 意图槽位 | 分类 + 抽槽 + 继承上下文 | 文本 + session | `{intent, slots, confidence}` | 置信度 < 0.6 → 澄清一次，仍低则兜底 |
| N2 查询类 | 调 T1/T2/T3/T10，组织答案 | slots | 文本 + 结构化卡片 | 工具失败 → 降级话术 + 转人工入口 |
| N3 退款判定 | 身份校验 → T4 | order_no, reason | `decision` | 校验失败 3 次 → 锁定 + 转人工 |
| N4 方案构建 | T5 建草稿，渲染方案卡 | decision | `refund_no + token + proposal` | 建单失败 → 提示稍后重试 |
| N5 确认闸门 | 等待用户确认/取消/修改 | 用户下一轮消息 | `CONFIRM/CANCEL/MODIFY` | 超时 → 草稿 `EXPIRED` |
| N6 执行分流 | T6 确认 → 自动或建审批 | token | `APPROVED / PENDING_APPROVAL` | 并发冲突 → 幂等返回首次结果 |
| N7 回写 | 状态事件、消息、审计、指标 | 全流程结果 | — | 异步，不阻塞回复 |
| N8 审批回调 | 审批结论转用户话术 | 审批事件 | 用户消息 | 任务过期 → 升级 + 告知 |

## 3. 会话状态机

### 3.1 状态图

```
INIT ──auth_ok──▶ AUTH_VERIFY ──intent_ok──▶ INTENT_RESOLVED
                          │                        │
                          │ 槽位缺失                ├──query──▶ TOOL_RUNNING ──▶ COMPLETED
                          ▼                        │
                   COLLECTING_SLOT ◀──缺槽──────────┘
                          │ 槽位齐
                          ▼
                   TOOL_RUNNING（判定）
                          │ eligible
                          ▼
                   PROPOSAL_PENDING ──cancel/timeout──▶ ABORTED / EXPIRED
                          │ user_confirm
                          ▼
                      EXECUTING
                     ╱          ╲
              自动通过            需审批
                │                  ▼
                │           PENDING_APPROVAL ──approve──▶ EXECUTING ──▶ COMPLETED
                │                  └──reject──▶ COMPLETED（告知拒绝）
                └──────────────────▶ COMPLETED

任意状态 ──user_request / risk / fallback×3──▶ ESCALATED
```

### 3.2 转移表（应用层强校验）

| # | from | event | to | 副作用 |
|---|---|---|---|---|
| 1 | INIT | session_created | AUTH_VERIFY | 建会话，签发临时 token |
| 2 | AUTH_VERIFY | auth_ok | INTENT_RESOLVED | 绑定 user_id |
| 3 | AUTH_VERIFY | auth_fail×3 | ESCALATED | 锁定 10 分钟，建工单 |
| 4 | INTENT_RESOLVED | need_slot | COLLECTING_SLOT | 追问 1 个槽位 |
| 5 | COLLECTING_SLOT | slot_filled | TOOL_RUNNING | — |
| 6 | COLLECTING_SLOT | give_up×2 | ESCALATED | 给"我的订单"选择器 |
| 7 | TOOL_RUNNING | query_done | COMPLETED | 推送答案 |
| 8 | TOOL_RUNNING | eligible | PROPOSAL_PENDING | **T5 建草稿 + token** |
| 9 | TOOL_RUNNING | rejected | COMPLETED | 解释 + 替代方案 |
| 10 | TOOL_RUNNING | need_evidence | COLLECTING_SLOT | 引导上传 |
| 11 | TOOL_RUNNING | tool_error×2 | ESCALATED | 带错误码建工单 |
| 12 | PROPOSAL_PENDING | user_confirm | EXECUTING | **T6，校验 token** |
| 13 | PROPOSAL_PENDING | user_cancel | ABORTED | 草稿 → CANCELLED |
| 14 | PROPOSAL_PENDING | user_modify | TOOL_RUNNING | 旧草稿作废，重新判定 |
| 15 | PROPOSAL_PENDING | token_expired | EXPIRED | 提示重新生成 |
| 16 | EXECUTING | auto_approved | COMPLETED | 写 outbox 执行 |
| 17 | EXECUTING | need_approval | PENDING_APPROVAL | 建审批任务，告知 SLA |
| 18 | PENDING_APPROVAL | approved | EXECUTING | 唤醒，执行 |
| 19 | PENDING_APPROVAL | rejected | COMPLETED | 话术说明原因 |
| 20 | PENDING_APPROVAL | sla_timeout | PENDING_APPROVAL | 升级并告知延迟 |
| 21 | 任意 | escalate | ESCALATED | 生成摘要 + 工单 |

非法跃迁（如 `PROPOSAL_PENDING → COMPLETED` 不经验证）直接抛 `4004` 并告警——这是防"跳过确认"的最后一道门。

### 3.3 状态持久化

```python
# 每次跃迁：校验 → 更新 → 落事件，三步同事务
def transit(session, event, payload=None):
    nxt = TABLE.get((session.state, event))
    if nxt is None:
        raise IllegalTransition(session.state, event)      # 4004
    prev, session.state = session.state, nxt
    db.update_session(session)                              # version 乐观锁
    db.insert_state_event(prev, nxt, event, payload)        # 事件溯源
```

## 4. 退款单状态机

```
DRAFT ──confirm──▶ USER_CONFIRMED ──auto──▶ APPROVED ──▶ PROCESSING ──▶ SUCCESS
  │                     │                                              └──FAILED
  │                     └──need_approval──▶ PENDING_APPROVAL
  │                                              │ approve ──▶ APPROVED
  │                                              └ reject ──▶ REJECTED_BY_HUMAN
  ├──cancel──▶ CANCELLED
  ├──timeout─▶ EXPIRED
  └──rule_reject──▶ REJECTED_BY_RULE（由判定直接写入，不建草稿）
```

| 状态 | 谁可写 | 允许的用户动作 |
|---|---|---|
| `DRAFT` | Agent | 确认 / 取消 / 改方案 |
| `ELIGIBLE` | 规则引擎 | 同上 |
| `USER_CONFIRMED` | 系统（瞬时态） | 无 |
| `PENDING_APPROVAL` | 审批人 | 催办 / 取消（可配置） |
| `APPROVED` | 系统 | 无 |
| `PROCESSING` | 清结算 | 无 |
| `SUCCESS` / `FAILED` | 清结算回调 | 失败可申请人工 |

## 5. Prompt 编排

### 5.1 分层提示词

| 层 | 内容 | 是否可变 |
|---|---|---|
| L1 系统人设 | 身份、语气、能力边界 | 版本管理，改需评审 |
| L2 硬约束 | 不得编造订单事实、不得承诺规则外结果、必须调工具才知道事实 | **不可被用户覆盖** |
| L3 流程指令 | 当前状态对应的动作（如"现在处于 PROPOSAL_PENDING，只做确认引导"） | 随状态注入 |
| L4 上下文 | 用户信息、槽位、工具结果 | 动态 |
| L5 输出格式 | 卡片 or 文本、字数限制 | 固定 |

### 5.2 按状态注入指令（关键）

不同状态下模型能做的事完全不同，靠提示词收窄自由度：

| 状态 | 注入的指令 |
|---|---|
| `COLLECTING_SLOT` | 只问缺失的一个槽位，不要解释规则，不要给方案 |
| `TOOL_RUNNING` | 不要输出任何结论，等待工具结果 |
| `PROPOSAL_PENDING` | 只复述方案要点 + 引导确认/取消；禁止说"已提交""已退款" |
| `PENDING_APPROVAL` | 只说明当前在审批中与预计时效；禁止承诺结果 |
| `COMPLETED` | 收尾 + 一句提醒（保留包装、留意到账） |

这条设计直接消灭了最常见的幻觉：**在用户还没确认时就说"已为您提交退款"**。

### 5.3 工具调用策略

| 策略 | 说明 |
|---|---|
| 强制首调 | 用户提到订单相关问题，必须先 `get_order`，不允许凭上下文猜 |
| 单轮上限 | 单轮最多 4 次工具调用，超限强制总结并给转人工入口（防死循环） |
| 并行 | `get_order` 与 `get_logistics` 可并行（无依赖） |
| 结果裁剪 | 工具结果只回灌必要字段（金额、状态、时间），避免上下文膨胀与信息泄露 |
| 失败语义 | 工具失败返回 `{ok:false, error:{code, retryable}}`，模型据此决定重试或转人工 |

### 5.4 输出前护栏

1. **承诺检测**：正则 + 小模型识别"保证/一定/马上到账/全额退"，命中改写。
2. **事实校验**：回答中出现的订单号、金额必须出现在工具结果里，否则拦截重生成。
3. **脱敏**：手机号、详细地址统一 `mask()`。
4. **长度与格式**：文本 ≤ 120 字，方案卡走结构化渲染。

## 6. 工具注册表

| 工具 | 入参 | 出参关键字段 | 副作用 | 幂等 |
|---|---|---|---|---|
| `get_order` | `order_no`, `user_no?` | status, items, amounts, delivered_at | 无 | 是 |
| `list_user_orders` | `user_no`, `limit` | 最近订单列表 | 无 | 是 |
| `get_logistics` | `order_no` | carrier, status, traces[3], eta | 无 | 是 |
| `check_refund_eligibility` | `order_no`, `reason_code`, `items` | eligible, decision_code, amount, approval_level | 无 | 是 |
| `create_refund_draft` | `fingerprint`, `session_no` | refund_no, confirm_token, proposal | 建 DRAFT | 按指纹 |
| `confirm_refund` | `refund_no`, `confirm_token` | status, next_action | **状态推进 + 建审批** | 需 key |
| `get_refund_status` | `refund_no` | status, node, eta | 无 | 是 |
| `cancel_refund` | `refund_no` | status | 状态变更 | 是 |
| `handoff_to_human` | `session_no`, `reason` | ticket_no, position | 建工单 | 是 |
| `search_faq` | `query` | 答案 + 出处 | 无 | 是 |

**权限矩阵**：`confirm_refund` 不直接给模型开放自由调用——模型只能调 `create_refund_draft`，`confirm_refund` 由编排层在收到用户明确确认后调用。这是"工具调用"与"业务安全"的分界点。

## 7. 人工审批编排

```
EXECUTING ──need_approval──▶ 创建 approval_tasks (level, sla_deadline)
                                    │
                          ┌─────────┴─────────┐
                          ▼                   ▼
                   审批工作台待办        企微/邮件通知（含一键通过链接）
                          │
              ┌───────────┼───────────┬──────────────┐
              ▼           ▼           ▼              ▼
          APPROVE      REJECT     TRANSFER    REQUEST_EVIDENCE
              │           │           │              │
        退款单APPROVED  置拒绝     新建任务      回 ELIGIBLE
              │           │                          │
              └─────┬─────┘                          ▼
                    ▼                          唤醒会话补材料
              发 outbox 事件
                    ▼
        会话被唤醒 → 生成用户话术 → 推送
```

**SLA 与升级**：定时任务每 5 分钟扫 `PENDING 且 sla_deadline < now()`，升级到上级并把任务 `level+1`，同时通知用户"处理时间会稍长，已加急"。

**越权防护**：审批结论只认 `approval_tasks` 表；用户说"你们主管已经同意了"不会影响任何状态。

## 8. 异常与恢复

| 场景 | 处理 |
|---|---|
| 服务重启 | 会话状态在 DB，凭 `session_no` 续跑；未完成的 `EXECUTING` 由补偿任务扫 `status=USER_CONFIRMED` 超 1 分钟的记录继续 |
| LLM 超时/限流 | 重试 1 次 → 降级为模板话术（"系统繁忙，已为你转人工"）+ 建工单 |
| 工具超时 | 800ms 快速失败，返回 `retryable=true`；模型最多重试 1 次 |
| 用户连续 3 轮兜底 | `fallback_count >= 3` → 自动 `ESCALATED` |
| 确认 token 过期 | 状态转 `EXPIRED`，引导"重新生成方案"，不自动重发 |
| 重复确认 | 幂等键命中，返回首次结果，提示"已提交，请勿重复操作" |
| 审批人长时间未处理 | SLA 升级 + 通知；超 24h 自动建投诉工单 |
| 退款执行失败 | 重试 3 次（1s/4s/16s），仍失败置 `FAILED` + 工单 + 用户告知 |

**补偿扫描任务**（每 1 分钟）：

1. `refund_requests.status IN ('USER_CONFIRMED') AND updated_at < now()-60s` → 继续执行
2. `refund_requests.status='PROCESSING' AND updated_at < now()-10min` → 查询清结算状态
3. `agent_sessions.state='PENDING_APPROVAL' AND expires_at < now()` → 保持（审批中会话不过期，仅标记不再主动推送）

## 9. 可观测设计

```
trace_id 贯穿：
  用户消息 → LLM 请求 → tool_call → 规则判定 → 退款单 → 审批 → outbox → 清结算

关键埋点：
  - 每轮对话：意图、置信度、状态迁移、工具序列、耗时、token 数
  - 每个决策：decision_code 分布、命中规则 TOP、自动/审批比例
  - 每个退款单：从确认到到账的时长分布（分自动/审批）
```

看板指标：`自动解决率`、`转人工率`、`平均轮次`、`工具错误率`、`审批积压`、`误退率`（人工抽检）。
