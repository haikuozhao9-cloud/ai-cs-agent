# 接口设计 · AI 客服与售后 Agent

> 完整机器可读契约：`api/openapi.yaml`。本文说明**为什么这么切分**、每个接口的契约细节与错误语义。

---

## 1. 分层与边界

```
┌─────────────────────────────────────────────┐
│ 渠道层  小程序 / APP / H5 / 客服工作台        │
└───────────────┬─────────────────────────────┘
                │ ① 对外 API（JWT，面向用户/坐席）
┌───────────────▼─────────────────────────────┐
│ Agent 编排服务（会话状态机 + LLM + 工具路由）  │
└───────────────┬─────────────────────────────┘
                │ ② 内部工具 API（mTLS，仅 Agent 可调）
┌───────────────▼─────────────────────────────┐
│ 业务服务（订单 / 物流 / 售后 / 支付）          │
└─────────────────────────────────────────────┘
                ▲
                │ ③ 回调 Webhook（物流商 / 清结算）
```

**三个原则**

1. **工具接口不面向终端**：`/internal/**` 需 mTLS + 服务白名单，禁止前端直连，否则规则可被绕过。
2. **对外接口不暴露决策细节**：用户只看到"可退/不可退 + 原因话术"，`decision_code`、规则阈值不对用户直出。
3. **写操作必带幂等键**：所有产生资金或状态变更的接口要求 `Idempotency-Key`。

## 2. 统一约定

### 2.1 响应信封

```json
{
  "code": 0,
  "message": "ok",
  "data": {},
  "trace_id": "tr_20261117_8f3a91c2",
  "server_time": "2026-11-17T18:30:00+08:00"
}
```

- `code=0` 成功；非 0 见错误码表。HTTP 状态码同时正确返回（400/403/404/409/429/500），便于网关治理。
- 业务失败（如"不可退"）**不是错误**：HTTP 200，`data.eligible=false`，`code=0`。只有系统异常才非 0。
- 所有响应带 `trace_id`，与 `agent_tool_calls.trace_id` 对齐。

### 2.2 鉴权

| 接口组 | 鉴权 |
|---|---|
| `/api/v1/agent/**` | 用户 JWT（含 `user_no`），匿名会话用临时访客 token |
| `/api/v1/approvals/**` | 员工 JWT + RBAC（`cs_leader` / `finance`） |
| `/internal/**` | mTLS 双向证书 + `X-Service-Name` 白名单 |
| `/webhooks/**` | 签名校验（HMAC-SHA256 + 时间戳 ±5min，防重放） |

### 2.3 幂等

- Header：`Idempotency-Key: <uuid>`，24h 内同 key 同 body 返回首次结果。
- 未传则服务端按 `session_no + intent + 方案指纹` 生成（降级方案，不推荐）。

### 2.4 错误码

| code | HTTP | 含义 | 客户端处理 |
|---|---|---|---|
| 0 | 200 | 成功 | — |
| 1001 | 400 | 参数校验失败 | 提示重填 |
| 1002 | 400 | 订单号格式非法 | 引导正确格式 |
| 2001 | 403 | 身份校验失败（尾号不符） | 提示重试，3 次锁定 |
| 2002 | 403 | 无权访问该订单 | 不披露信息 |
| 3001 | 404 | 订单不存在 | 提供最近订单 |
| 3002 | 404 | 退款单不存在 | — |
| 4001 | 409 | 重复提交（幂等命中） | 返回首次结果，提示勿重复 |
| 4002 | 409 | 订单已有进行中退款 | 展示进度 |
| 4003 | 409 | 方案已失效（token 过期） | 重新生成方案 |
| 4004 | 409 | 状态不允许该操作（状态机拒绝） | 刷新状态 |
| 5001 | 500 | 工具下游超时 | 可重试，前端展示降级 |
| 5002 | 500 | 规则引擎异常 | 转人工 |
| 5003 | 429 | 触发限流 | 退避重试 |
| 6001 | 403 | 审批越权 | 提示无权限 |
| 6002 | 409 | 审批任务已被处理 | 刷新待办 |

## 3. 对外接口

### 3.1 `POST /api/v1/agent/chat` — 对话（SSE 流式）

**为什么流式**：首字延迟直接决定体验，Agent 要先调 2~3 个工具再回答，同步等待会超过 3 秒。

请求：

```json
{
  "session_no": "S20261117A001",
  "user_no": "U1001",
  "message": "我上周买的开衫不想要了，订单 ORD20261101001，能退吗",
  "channel": "APP",
  "client_msg_id": "c_88f1"
}
```

`session_no` 为空则新建会话。

SSE 事件序列：

| event | data | 说明 |
|---|---|---|
| `ack` | `{session_no, state}` | 已受理，返回会话号 |
| `state` | `{from, to, event}` | 状态跃迁（前端可展示"正在查询订单…"） |
| `tool_call` | `{tool_name, args_digest}` | 工具开始（脱敏后摘要） |
| `tool_result` | `{tool_name, ok, latency_ms}` | 工具结束 |
| `token` | `{text}` | 增量文本 |
| `card` | `{type:"refund_proposal", payload:{...}}` | 方案卡（结构化，前端渲染） |
| `done` | `{state, need_confirm, confirm_token}` | 本轮结束 |
| `error` | `{code, message, fallback:"HUMAN"}` | 异常 |

方案卡 payload：

```json
{
  "refund_no": "RF202611170001",
  "refund_type": "RETURN_REFUND",
  "refund_type_text": "退货退款",
  "amount_detail": {
    "goods": 299.00,
    "freight_refund": 0.00,
    "freight_deduct": 0.00,
    "discount_deduct": 0.00,
    "total": 299.00
  },
  "return_method": "上门取件",
  "eta": "审核通过后 1-3 个工作日原路退回",
  "need_user_action": ["保持商品吊牌完好", "预约上门取件时间"],
  "confirm_token": "ct_9f2b...",
  "expire_at": "2026-11-17T18:45:00+08:00"
}
```

### 3.2 `POST /api/v1/agent/confirm` — 确认 / 取消方案

```json
{ "session_no": "S20261117A001", "refund_no": "RF202611170001", "action": "CONFIRM", "confirm_token": "ct_9f2b..." }
```

| 字段 | 规则 |
|---|---|
| `action` | `CONFIRM` / `CANCEL` |
| `confirm_token` | CONFIRM 必填，一次性，10 分钟有效，服务端只存哈希 |

响应：

```json
{
  "code": 0,
  "data": {
    "refund_no": "RF202611170001",
    "status": "PENDING_APPROVAL",
    "next_action": "WAIT_APPROVAL",
    "need_manual_approval": true,
    "approval_level": 1,
    "sla_deadline": "2026-11-17T22:30:00+08:00",
    "user_message": "已提交，客服主管将在 4 小时内处理，结果会通过消息通知你"
  }
}
```

错误：`4003` token 过期 / `4004` 状态不允许 / `4001` 重复确认（返回首次结果）。

**关键约束**：此接口是唯一能把退款单从 `DRAFT/ELIGIBLE` 推进到 `USER_CONFIRMED` 的入口。LLM 无法直接调用它（工具层只暴露 `confirm_refund`，且必须携带服务端签发 token）。

### 3.3 `GET /api/v1/agent/sessions/{session_no}` — 会话回看

返回状态、槽位摘要、最近 20 条消息（含工具调用摘要）。坐席接管时用。

### 3.4 `POST /api/v1/agent/handoff` — 转人工

```json
{ "session_no": "S20261117A001", "reason": "USER_REQUEST", "priority": 1 }
```

服务端生成结构化摘要（`service_tickets.summary`），返回 `ticket_no` 与排队位次。摘要模板：

```
用户诉求：退款（订单 ORD20261101001，299 元，已签收 3 天）
已查：订单已签收、物流已妥投、类目 APPAREL 支持 7 天无理由
已判：OK_AUTO，方案已展示，用户未确认即要求人工
疑点：用户提到"线头多"，可能主张质量问题
建议：核实商品照片，可走质量问题免运费退回
```

### 3.5 `GET /api/v1/refunds/{refund_no}` — 退款进度

返回状态、金额、当前节点、审批进度、预计到账。用户侧高频轮询接口，加 60s 缓存。

### 3.6 `GET /api/v1/traces/{trace_id}` — 全链路（内部/审计）

按 trace 拉取：消息、工具调用、状态事件、审批、退款变更。用于客诉复盘。

## 4. 审批接口（人工审批）

### 4.1 `GET /api/v1/approvals` — 待办列表

Query：`status=PENDING&level=1&page=1&size=20&sort=sla_deadline`
返回含 `refund_no`、`order_no`、`amount`、`decision_code`、`reasons[]`、`sla_remaining_seconds`、`user_summary`。

### 4.2 `POST /api/v1/approvals/{task_no}/decision` — 审批决策

```json
{
  "decision": "APPROVE",
  "approved_amount": 1800.00,
  "comment": "核对物流拦截成功，同意退 1800（扣 80 运费）",
  "transfer_to": null
}
```

| decision | 效果 |
|---|---|
| `APPROVE` | 退款单 → `APPROVED`，触发执行；可改额，差额写 `decision_payload` |
| `REJECT` | 退款单 → `REJECTED_BY_HUMAN`，`comment` 必填，回传用户话术 |
| `TRANSFER` | 转他人/上级，任务 `TRANSFERRED`，新建任务 |
| `REQUEST_EVIDENCE` | 退回补充材料，退款单回 `ELIGIBLE`，会话被唤醒 |

约束：

- 审批人须具备对应 `level` 角色，否则 `6001`。
- 任务状态非 `PENDING` 时返回 `6002`（防重复点击/抢单冲突）。
- 审批完成后发 `outbox_events(REFUND_APPROVED/REJECTED)`，Agent 通过消息通道通知用户。

### 4.3 `GET /api/v1/approvals/stats` — 审批健康度

待办积压、平均处理时长、超时率、通过率。运营看板数据源。

## 5. 内部工具接口

统一前缀 `/internal/tools`，统一返回：

```json
{
  "ok": true,
  "data": {},
  "error": null,
  "meta": { "trace_id": "...", "latency_ms": 42, "cache": "HIT", "version": 3 }
}
```

失败时 `ok=false`，`error: {code, message, retryable}`。**工具永不抛 5xx 给 LLM**，必须转成结构化错误，让模型能读懂并决定重试/转人工。

| # | 方法 | 路径 | 用途 | 幂等 |
|---|---|---|---|---|
| T1 | GET | `/orders/{order_no}` | 订单详情（含明细、金额） | 是 |
| T2 | GET | `/users/{user_no}/orders?limit=3` | 最近订单（无单号时兜底） | 是 |
| T3 | GET | `/logistics?order_no=` | 物流状态 + 最近 3 条轨迹 | 是 |
| T4 | POST | `/refund/eligibility` | 资格判定（纯计算，不落单） | 是 |
| T5 | POST | `/refund/draft` | 生成方案草稿 + confirm_token | 是（按方案指纹） |
| T6 | POST | `/refund/confirm` | 确认并推进状态 | **否，需 Idempotency-Key** |
| T7 | POST | `/refund/{refund_no}/execute` | 提交清结算（审批后由系统调） | 是 |
| T8 | GET | `/refund/{refund_no}` | 退款单详情 | 是 |
| T9 | POST | `/refund/{refund_no}/cancel` | 取消（仅 DRAFT/ELIGIBLE） | 是 |
| T10 | GET | `/faq?q=` | 知识库检索 | 是 |

### 5.1 T4 `POST /refund/eligibility`

请求：

```json
{
  "order_no": "ORD20261101001",
  "reason_code": "NO_REASON",
  "refund_type": "AUTO",
  "items": [{ "order_item_id": 1, "qty": 1 }],
  "evidence_urls": [],
  "as_of": "2026-11-17T18:30:00+08:00"
}
```

响应（核心）：

```json
{
  "ok": true,
  "data": {
    "eligible": true,
    "decision_code": "OK_AUTO",
    "refund_type": "RETURN_REFUND",
    "amount": { "goods": 299.00, "freight_refund": 0.00, "freight_deduct": 0.00, "discount_deduct": 0.00, "total": 299.00 },
    "need_manual_approval": false,
    "approval_level": 0,
    "requires_evidence": false,
    "reasons": ["已签收 3 天，在 7 天无理由期内"],
    "hit_rules": ["BR-01", "BR-05", "BR-12"],
    "policy_version": 3,
    "fingerprint": "sha256:1a2b..."
  }
}
```

`fingerprint` = 订单号 + 明细 + 金额 + 规则版本 + 原因 的哈希，`/refund/draft` 用它做幂等与防篡改。

### 5.2 T5 `POST /refund/draft`

请求 `{ "fingerprint": "sha256:1a2b...", "session_no": "S..." }`
响应 `{ "refund_no": "RF...", "status": "DRAFT", "confirm_token": "ct_...", "expire_at": "...", "proposal": {...} }`

- 只写 `refund_requests(status=DRAFT)`，**不触发任何资金动作**。
- 同 `fingerprint` 重复调用返回同一 `refund_no`（不重复建单）。
- 一个会话同时只允许一个有效草稿，新建则旧草稿置 `CANCELLED`。

### 5.3 T6 `POST /refund/confirm`

```json
{ "refund_no": "RF...", "confirm_token": "ct_...", "idempotency_key": "idem_..." }
```

状态机：`DRAFT/ELIGIBLE → USER_CONFIRMED → (PENDING_APPROVAL | APPROVED)`。

- token 校验失败 → `4003`；重复 → `4001` 返回首次结果。
- 需审批时同事务创建 `approval_tasks` 并置 `PENDING_APPROVAL`。

### 5.4 T7 `POST /refund/{refund_no}/execute`

仅接受 `APPROVED` 状态；写 `outbox_events`；返回 `{status:"PROCESSING", outbox_id}`。由审批回调或自动通过流程触发，**不暴露给 LLM**（不给模型直接动钱的能力）。

## 6. Webhook

### 6.1 `POST /webhooks/logistics`

物流商推送轨迹。校验签名 → 更新 `shipments` + 追加 `shipment_traces` → 若状态变为 `SIGNED` 且订单未同步，回填 `orders.delivered_at`（**BR-05 基准，必须准确**）→ 若存在 `PROPOSAL_PENDING` 会话，向用户推送"已签收，售后期开始计算"。

### 6.2 `POST /webhooks/payment-refund`

清结算退款结果。`SUCCESS` → 退款单 `SUCCESS`、订单 `after_sale_status` 更新、累加 `refunded_amount`、发通知；`FAILED` → 重试 3 次后置 `FAILED` 并建工单。

## 8. 版本与兼容

- URL 带主版本 `/v1`；新增字段向后兼容，删除/改语义升 `/v2`。
- 工具接口变更需同步更新 `prototype/tools_schema.json` 与提示词中的工具描述，二者必须一致，否则模型会传错参。
- SSE 新增事件类型时，旧前端应忽略未知 `event`（前端需做默认忽略分支）。
